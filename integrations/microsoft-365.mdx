NEXOS CORE connects to Microsoft 365 through the Microsoft Graph API. There's no
single "M365 module" — Graph powers a handful of features, which share **one
per-tenant app registration** using app-only (client-credentials) auth.

## Setup

Configure a Microsoft 365 connection under **Settings → Integrations** (an email
account with provider Microsoft 365): your **tenant ID, client ID, and client
secret** from an Entra app registration. NEXOS CORE fetches and caches app-only
tokens automatically.

The app registration needs these **application** permissions (admin-consented):
`Calendars.ReadWrite`, `Mail.Read` + `Mail.ReadWrite`, and `Mail.Send`.

## Restrict outbound send to one mailbox

`Mail.Send` is an **application** permission, so by default the app registration
can send as **any mailbox in your tenant**. Scope it to the single mailbox NEXOS
CORE should send from.

This step is not optional on newer tenants: without it, outbound send is refused
outright. Which command you use depends on which model your tenant is on, and
Microsoft is midway through migrating everyone from one to the other.

**Check first — this one command decides everything:**

```powershell
Connect-ExchangeOnline -UserPrincipalName <you>@yourdomain.com
Get-ServicePrincipal | Format-List DisplayName, AppId
```

### If it returns nothing — RBAC for Applications

Your tenant uses the current model. You need the **enterprise application's**
Object ID from Entra — *Enterprise applications → your app → Object ID*. That is
not the same value as the app registration's Object ID.

```powershell
New-ServicePrincipal -AppId <client-id> `
  -ObjectId <enterprise-app-object-id> `
  -DisplayName "NEXOS CORE"

New-ManagementScope -Name "NEXOS CORE Senders" `
  -RecipientRestrictionFilter "PrimarySmtpAddress -eq 'support@yourdomain.com'"

New-ManagementRoleAssignment -App <service-principal-id> `
  -Role "Application Mail.Send" `
  -CustomResourceScope "NEXOS CORE Senders"
```

The management scope is the security boundary. Without it the role applies
tenant-wide and the app can send as anyone.

### If it returns entries — legacy Application Access Policy

```powershell
New-DistributionGroup -Name "NEXOS CORE Senders" `
  -Alias nexos-senders -Type Security `
  -Members support@yourdomain.com

# Use the address this returns — usually @yourtenant.onmicrosoft.com,
# NOT your vanity domain.
Get-DistributionGroup -Identity nexos-senders | Select PrimarySmtpAddress

New-ApplicationAccessPolicy -AppId <client-id> `
  -PolicyScopeGroupId <that-address> `
  -AccessRight RestrictAccess `
  -Description "NEXOS CORE outbound only"
```

<Note>
Binding to the vanity domain instead of the real `PrimarySmtpAddress` produces a
policy that denies everything while reporting healthy.
</Note>

## Before mail will actually arrive

Microsoft accepting a message is not the same as it being delivered. The sending
domain needs working email authentication, or recipients — Gmail especially, which
has rejected unauthenticated mail since February 2024 — will drop it silently.

| Record | Value |
|---|---|
| **SPF** | must include `spf.protection.outlook.com` |
| **DKIM** | `selector1` / `selector2` CNAMEs from the Defender portal, then **Enable** |
| **DMARC** | `v=DMARC1; p=none; rua=mailto:dmarc@yourdomain.com` to start |

If you previously sent through a filtering service and have since moved MX to
Microsoft, remove the old provider from SPF — a record describing a path you no
longer use will fail.

## Troubleshooting outbound send

**`403 ErrorAccessDenied` — "Access to OData is disabled: [RAOP] : Blocked by
tenant configured AppOnly AccessPolicy settings"**

This message is misleading. It names *Application Access Policy*, the **legacy**
model — but on a tenant using RBAC for Applications it actually means **the app
has no Exchange role assignment**. Creating an access policy will not help.

Run `Get-ServicePrincipal` and follow whichever tab above applies.

Two things that will mislead you while diagnosing:

- **`Test-ApplicationAccessPolicy` returns `Granted` on an RBAC tenant and means
  nothing.** It evaluates the legacy store, which no longer governs access.
- **A valid token is not proof.** The token legitimately carries
  `roles: ["Mail.Send"]` because Entra granted the permission. Exchange refuses it
  separately, at a later stage.

**Mail sends successfully but never arrives** — that is delivery, not permissions.
Check the DNS records above, and confirm the message is in the sending mailbox's
Sent Items.

## What it powers

- **Calendar sync** — [Dispatch](/dispatch) creates, updates, and deletes events
  on a technician's M365 calendar when you assign, change, or remove a dispatch
  slot (one-way, NEXOS CORE → M365).
- **Email-security mailbox tap** — [Email security](/emailsec/index) reads recent
  messages (with full headers) for phishing analysis and moves flagged mail to
  Junk.
- **Outbound email** — quote and invoice delivery can send through Graph
  (`sendMail`).
- **Microsoft SSO** — staff can sign in with "Microsoft" via OIDC (a separate
  login flow from the app-only credentials above).

## What is *not* integrated

To set expectations clearly, NEXOS CORE's Graph usage is limited to calendar,
mail, and sign-in. There is **no** integration for:

- Microsoft Teams / chat
- SharePoint or OneDrive
- Intune / device management
- Entra user or group sync / provisioning
- Defender / Secure Score pull (email security uses the headers already stamped by
  Defender/Inky, not a security API)

## Good to know

- **One shared app registration** serves calendar sync, the mailbox tap, and
  outbound send — a single client secret spans all three.
- Permissions are **application-scoped (org-wide)**, not per-user delegated.
- The email-security tap monitors **one mailbox per tenant** (the first configured
  Microsoft 365 account).
